# C07 — Preuves, tests et budgets


## Enregistrement d’exécution
Une preuve contient TestId, statut PASS/FAIL/BLOCKED/NOT_RUN, UTC, commit, build, version du jeu/runtime, identité géographique, seed, profil, zone, commande/capacité MCP réellement utilisée et liens vers fichiers. Les métriques sont numériques avec unités. La sortie standard résumée ne remplace pas le TRX ou rapport structuré original.

Un rapport n’expose pas le token MCP, les secrets, les comptes du jeu ou chemins personnels inutiles. Un screenshot indique l’endroit et l’angle ; un test de navigation conserve le profil et le chemin évalué. Un test de panne précise l’étape de coupure.

## Statuts de travail
BACKLOG → READY → IN_PROGRESS → REVIEW → DONE. BLOCKED est un état distinct avec cause et condition de reprise. READY exige que tous les prérequis soient DONE au commit intégré. L’auteur propose ; l’intégrateur met à jour le registre. Une tâche n’est pas DONE parce que son code existe ou que son auteur juge les tests probablement verts.

## Oracles
Les tests analytiques utilisent solutions/volumes connus ; les tests de propriétés utilisent invariants ; les tests d’intégration inspectent le moteur réel ; les revues de qualité utilisent une grille. Un golden hash n’est mis à jour qu’après justification d’un changement intentionnel de modèle/version. Le rafraîchir automatiquement pour faire passer CI est interdit.

Les seuils de corpus et de tolérance sont dans les fiches T*. Les budgets performance/statistiques peuvent commencer PROPOSED mais doivent devenir FROZEN avant la recette concernée. Changer un seuil après mesure exige un ADR et une nouvelle campagne ; les anciennes mesures restent conservées.

## Gate de release
Zéro échec/NOT_RUN pour tests bloquants, aucun deadlock/corruption/site fantastique inaccessible dans les cas publiés, preuve de configuration/support, package nettoyé et parcours humain validé. Un défaut cosmétique mineur peut être documenté avec accord de revue ; il ne permet pas de contourner un invariant géographique ou de sauvegarde.

La portée de chaque PASS est limitée au corpus/version/matériel enregistrés. Les preuves du validateur documentaire portent uniquement sur ce cahier des charges : elles ne valident ni le code futur, ni l’API locale, ni les temps de génération.
