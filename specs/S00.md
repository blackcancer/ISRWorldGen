# S00 — Environnement, API et preuve d’intégration

**Normatif · lot L00 · v1.0.**

## Objet
Lever les risques d’intégration avant de produire un monde complet. L’IDE de travail est Visual Studio Community 2026, avec le template Vintage Story déjà installé. Le fichier `{NomDuMod}ModSystem.cs` du template reste le point de départ. Les méthodes Start, StartServerSide et StartClientSide sont adaptées à leur rôle réel ; les messages du template ne constituent pas une preuve d’injection terrain.

## Audit obligatoire
Relever version exacte du client et du serveur, chemins locaux, TargetFramework/runtime réellement utilisé, versions et empreintes des DLL référencées, SDK disponible, configuration Debug, symboles, architecture et extension MCP. Conserver ces informations dans un rapport local expurgé des secrets. Geler un `global.json` seulement après cette observation. La documentation en ligne 1.22.7 sert de référence documentaire, pas d’autorisation à changer l’installation.

Le premier essai du générateur utilise une sauvegarde jetable séparée et un terrain synthétique minuscule. Il doit démontrer la prise de contrôle de la bonne passe, la présence des blocs et fluides, la mise à jour des métadonnées et le retour aux autres phases prévues. Il ne faut pas remplacer silencieusement tous les générateurs.

## Stratégie d’injection
La voie privilégiée est le type de monde standard avec activation explicite par configuration et remplacement ciblé des handlers incompatibles, uniquement si la version testée permet d’en prouver l’ordre et l’identité. Le schéma exact est arrêté dans un ADR après inspection du jeu. Une alternative de type de monde dédié nécessite un inventaire des générateurs vanilla à réinscrire et une nouvelle preuve de compatibilité ; elle n’est pas un raccourci automatique.

Le terrain, la stratification, les rivières, les cavernes et les remplissages de lacs natifs doivent être classés « conservé / remplacé / adapté ». Les fonctions de lumière, décor, structures, minerais et story sont inventoriées séparément. Interdire WipeAllHandlers global, appels à des événements imaginaires et patch JSON supposé supprimer un ModSystem C#.

## Dépendances
VintagestoryAPI est la référence obligatoire de l’adaptateur. Les références aux assemblages de survie/essentials sont ajoutées seulement pour des types effectivement utilisés. Le cœur préfère la bibliothèque standard. Les bibliothèques supplémentaires disponibles dans l’installation ne sont pas activées globalement. Newtonsoft.Json ou protobuf-net peuvent être retenus pour des besoins identifiés, en vérifiant la version embarquée ; 0Harmony reste désactivé sauf décision spécifique et justification. Les bibliothèques de tests restent hors package runtime.

Les observations vérifiées figurent dans `docs/04-AUDIT-API.md`, sources API-01 à API-08. Les commandes de débogage sont décrites par capacités et non par noms d’outils MCP inventés.

## Exigences vérifiables

### R00-01
La cible exacte du jeu, du runtime et des assemblages doit être relevée et verrouillée avant tout code dépendant de l’API.

### R00-02
Le template doit compiler en Debug et Release et le package doit charger une seule instance du mod sans double DLL.

### R00-03
Codex doit pouvoir atteindre un breakpoint C# dans le processus réel du jeu via le MCP, avec symboles correspondant au commit.

### R00-04
La prise de contrôle de worldgen doit être ciblée, traçable et limitée aux nouveaux mondes explicitement activés.

### R00-05
La preuve initiale doit valider blocs solides, fluides et métadonnées sur la même colonne réelle.

### R00-06
L’initialisation, la sauvegarde, la fermeture et le rechargement doivent libérer les handlers/ressources sans duplication.

## Validation
Les cas [T00](../tests/T00.md) sont obligatoires. Les tâches L00-A/B/C définissent le périmètre exact de chaque livraison.
